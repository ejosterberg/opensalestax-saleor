## SonarQube hotspot dispositions

Three hotspots were flagged on the initial scan. All three were
the same pattern: `str.replace(/\/+$/, '')` to strip trailing
forward slashes from a URL. SonarQube's `typescript:S5852` rule
flags the `+` quantifier next to `$` as a ReDoS surface, but the
quantifier is on a single literal character — the regex is
mathematically O(n) safe (no nested or alternating quantifiers).

**Disposition:** Fixed in commit (see git log) by lifting the
operation into `stripTrailingSlashes()` in `src/lib/url.ts`, a
non-regex imperative helper. Cleaner, equally correct, no static
analyzer alarms.

| Hotspot ID | File | Line | Disposition |
|---|---|---|---|
| `72304383...` | `src/lib/config.ts` | 97 | Fixed (refactored to `stripTrailingSlashes`) |
| `3be1dd77...` | `src/lib/config.ts` | 98 | Fixed (same refactor) |

## OWASP A01 — Broken access control

- [x] Every webhook handler verifies the Saleor JWT before reading
  payload contents. JWT verification is delegated to
  `@saleor/app-sdk`'s `SaleorSyncWebhook.createHandler` — the SDK
  wraps the user-supplied callback in a signature-verifying
  pipeline. Constitution §7 makes this non-negotiable; our code
  never reaches into the payload before the SDK has verified.
- [x] `/api/register` requires Saleor's domain + bearer token,
  enforced by `createAppRegisterHandler` from the SDK.
- [x] The APL is consulted before the handler runs (the SDK does
  this); unknown `saleorApiUrl` results in 401.
- [x] No debug / test endpoints exposed in production. The only
  routes are `/api/manifest`, `/api/register`, the two webhooks,
  and `/health`. `/health` returns a small JSON blob (engine
  status, version, RTT). No data exfiltration surface.

## OWASP A02 — Cryptographic failures

- [x] JWT signature verification uses Saleor's JWKS, fetched from
  the installed Saleor instance per the SDK's `EnvAPL` /
  `AuthData` flow. JWKS responses are cached with a 5-minute TTL
  (SDK default), refetched on signature failure.
- [x] OST API tokens read from `OSTAX_API_KEY` env var only; not
  logged (verified by inspection: structured log calls in
  `tax-handler.ts` log `{event, saleorApiUrl, line_count, ...}`
  but never the API key, the customer address, or product names).
- [x] No hardcoded keys / tokens. `grep -rn 'eyJ\|sk_\|pk_\|Bearer
  ' src/` returns no matches.
- [x] TLS not disabled on outbound. `OpenSalesTaxClient.request`
  uses global `fetch` with no `agent` option; Node's default
  rejects bad certs. No `NODE_TLS_REJECT_UNAUTHORIZED=0`
  references anywhere.

## OWASP A03 — Injection

- [x] OST API requests use JSON-serialized objects — no string
  concatenation of payload fields into URLs or bodies. Path is
  fixed (`/v1/calculate`, `/v1/health`); never built from user
  input.
- [x] Log statements use structured logging (the `console.*`
  wrappers in `tax-handler.ts` JSON-serialize a context object;
  no string interpolation of user-controlled fields).
- [x] No `eval`, `Function(...)`, or `child_process.exec` anywhere
  in `src/`. Verified by grep.

## OWASP A04 — Insecure design

- [x] Fail-soft behavior documented (README, CHANGELOG, constitution
  §8) and tested (`tax-handler.test.ts`: "fail-soft: returns empty
  response on engine error").
- [x] Fail-hard mode (`OSTAX_FAIL_HARD=1`) tested too — throws
  `TaxCalculationError` which the SDK formats as a webhook error
  response (Saleor surfaces it to the checkout flow).
- [x] Non-USD currency / non-US country short-circuits to empty
  response in `buildOstRequest`; engine never called. Tested.
- [x] No silent failures: every `catch` in production code logs a
  structured ERROR (`tax-handler.ts:engine_error`,
  `server.ts:server.uncaught`, `ostax-client.ts` throws typed
  errors).

## OWASP A05 — Security misconfiguration

- [x] Dockerfile runs as the unprivileged `node` user (`USER node`
  before `CMD`).
- [x] docker-compose.yml does not expose the OST engine on a host
  port by default (commented out, with a note that it's for
  debugging only). Postgres also internal-only. Only the app's
  port 3000 is published.
- [x] `NODE_ENV=production` is set in the Dockerfile's runtime
  stage.
- [x] Stack traces are not emitted in 5xx response bodies. The
  catch-all in `server.ts` writes only `{"error": "Internal
  Server Error"}` — the actual error message goes to stdout for
  the operator.
- [x] CORS not enabled — Saleor webhook calls are server-to-server.
  No browser origin path.

## OWASP A07 — Identification & authentication failures

- [x] No password-based auth surface. All auth is JWT (Saleor
  signing keys via JWKS) or APL bearer token (one-time install).
- [x] Token replay: Saleor's JWTs carry standard `iat` / `exp`
  claims, validated by the SDK's `jose`-based pipeline.
- [x] Verified by the negative test in `server.test.ts`:
  "webhook endpoint rejects unauthenticated requests" — POST
  without a valid signature returns 4xx.

## OWASP A08 — Software & data integrity failures

- [x] `package-lock.json` committed.
- [x] CI runs `npm ci` (lockfile-strict), not `npm install`. Audit
  step enforced (`npm audit --omit=dev --audit-level=high`).
- [x] No `postinstall` scripts in this project's `package.json`.
  Transitive `postinstall` scripts are reviewed by `npm audit` /
  `npm ls` periodically.
- [x] Dockerfile uses `npm ci` (lockfile-strict) in the build stage
  and then `npm prune --omit=dev` to strip dev deps before
  copying into runtime.

## OWASP A09 — Security logging & monitoring failures

- [x] Webhook receipts log `{event, saleorApiUrl, line_count}` only
  — verified by the negative test in `tax-handler.test.ts`
  ("does not include customer addresses or product names in log
  calls"). PII columns (postalCode, countryArea, line.id) are NOT
  in the structured log.
- [x] Authentication failures handled by the SDK and bubbled up
  via its `WebhookError` format; logged as part of the SDK's
  built-in error path.
- [x] OST engine errors logged at ERROR with HTTP status + rtt_ms
  (`tax-handler.ts:tax_calc.engine_error`).
- [x] Logs go to stdout (12-factor). No file logging.

## OWASP A10 — Server-side request forgery

- [x] `OSTAX_API_URL` validated as `http:` / `https:` URL at boot
  in `loadConfig`. Request-time interpolation: only fixed paths
  are appended (`/v1/calculate`, `/v1/health`).
- [x] JWKS fetch URL is constructed by the SDK from the
  `saleorApiUrl` validated at install time. Custom-scheme URLs
  (file:, javascript:, data:) are rejected by both the SDK and by
  our `validateUrl` helper.
